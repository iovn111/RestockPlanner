# Спецификация проекта Restock Planner

Рабочее название продукта: **Restock Planner** (русское название — выбрать позже).
Формат продукта: **десктопное приложение для Windows**, работающее офлайн; интернет нужен только для загрузки данных по API.
Документ — единый источник правды для разработки и для текста курсовой.

---

## 1. Контекст работы

- Курсовая работа, 3 курс, направление «Бизнес-информатика», ОП «Разработка информационных систем для бизнеса».
- Требования кафедры этого года: упор на **научную новизну** и **практическую пользу**; результат должен быть похож на реальный проект — **готовый продукт**, которым потенциальный покупатель может пользоваться; **простота освоения и использования**.
- Работа должна иметь задел на ВКР (см. раздел 11).

## 2. Проблема

Небольшой продавец на Wildberries / Ozon постоянно решает: **сколько и когда заказать у поставщика**.
- Заказал мало → товар закончился → упущенные продажи, карточка теряет позиции в поиске.
- Заказал много → деньги заморожены в товаре, маркетплейс берёт плату за хранение.
- Обычно считают «на глаз» или в Excel: «средние продажи × дни − остаток».

Две системные ошибки такого расчёта:
1. **Дефицит искажает историю.** Если товар (или ходовые размеры) закончился, продажи в эти дни занижены, хотя спрос был. Прогноз по таким данным занижается → снова дефицит → порочный круг.
2. **Новинки без истории.** Для нового товара считать не по чему; селлер гадает.

## 3. Целевой пользователь

- Селлер малого/среднего масштаба: 20–300 SKU, работает по FBO, часто — одежда/обувь (размерная сетка).
- Нет аналитика в штате; не хочет платить 5–20 тыс. ₽/мес за большой аналитический комбайн.
- Закупает у поставщика с длительным сроком (производство, доставка из Китая 30–60+ дней).
- Ценит: «скажи, сколько заказать и почему» без настройки параметров.

## 5. Методы (научная часть)

Общий конвейер:
```
Данные (продажи, остатки по размерам по дням, атрибуты товаров)
  → [5.1] Восстановление спроса  → очищенный ряд «сколько хотели купить»
  → [5.2] Прогноз: обычные товары — ETS; новинки — аналоги + смешивание
  → [5.3] Расчёт заказа: спрос за срок поставки + страховой запас по эмпирическим ошибкам
  → Рекомендация: «заказать N шт. до даты D, риск дефицита X%» + объяснение
```

### 5.1 Восстановление спроса при дефиците

Термины в литературе: censored demand, unconstraining, demand estimation with stockouts, lost sales.

**Шаг 1. Коэффициент доступности `a_t ∈ [0, 1]` за каждый день t.**
- Для товаров с размерами: доли размеров `s_i` оцениваются по дням полной доступности (все размеры в наличии), **только по прошлому** относительно даты расчёта. `a_t = Σ s_i` по размерам, бывшим в наличии в день t.
- Для товаров без размеров: `a_t = 1`, если остаток > 0, иначе 0.
- Если долей по истории недостаточно — равномерное распределение или доли по категории (зафиксировать в DECISIONS.md).

**Шаг 2. Восстановление.**
- Если `a_t ≥ τ` (гипотеза τ = 0.3, подбирается экспериментально): `demand_t = sales_t / a_t`.
- Если `a_t < τ` (включая 0): `demand_t` = среднее по ближайшим «чистым» дням (a = 1) в окне ±2–4 недели с поправкой на день недели (мультипликативный коэффициент дня недели, оценённый по прошлому).

**Почему не Тобит / EM:** моменты дефицита нам известны напрямую (дневные остатки), а продажи малых селлеров — малые целые числа (0, 1, 3…), что нарушает предпосылку нормальности Тобит-модели. Метод должен объясняться одним примером.

**Вне MVP (на диплом):** дефицит по складам/регионам, влияние малого остатка на позицию в поиске.

### 5.2 Прогноз

**Обычные товары:** экспоненциальное сглаживание (ETS, `statsforecast`) по восстановленному спросу. Опционально для сравнения — методы для прерывистого спроса (Croston/TSB), если продажи сильно разрежены (решение фиксировать в DECISIONS.md).

**Новинки (холодный старт).** Термины: new product forecasting, cold start, analog forecasting.
1. **Аналоги:** 3–5 ближайших товаров из каталога того же селлера по признакам: категория (предмет WB / категория Ozon), log(цена), ключевые характеристики (материал, сезон, пол и т. п.). Используем «кривую запуска» аналогов — восстановленный спрос по неделям с даты первой продажи, нормированный при необходимости.
2. **Запасные варианты** (по порядку): аналоги из близкой категории с поправкой на цену → среднее по категории в каталоге → выбор аналога пользователем (система предлагает 3, пользователь подтверждает одним нажатием) → ожидание пользователя («3–5 шт./день»).
3. **Смешивание:** `forecast = w · own + (1 − w) · analog`, `w = n / (n + k)`, n — дней продаж новинки, k — гипотеза 14, подбирается экспериментально. Это упрощённая байесовская (shrinkage) схема.

**Почему не глобальная модель (LightGBM):** у малого селлера 30–300 товаров — недостаточно для обучения; хуже объяснимость. Глобальная модель — на диплом.

### 5.3 Расчёт заказа и риска

- Модель — периодическая проверка до целевого уровня (R, S).
- Горизонт = срок поставки от поставщика L (единственная обязательная настройка пользователя) + период до следующего заказа R (по умолчанию 30 дней; гипотеза, подбирается в симуляции 6.4, не обязательная настройка).
- Прогнозируются **заказы** (спрос); расход склада = прогноз заказов × процент выкупа (вычисляется автоматически: товар → категория → значение по умолчанию).
- Объём заказа: `N = max(0, расход за (L + R) + страховой запас − остаток − товар в пути на склады МП − уже заказано у поставщика)`.
- Дата «заказать до» D — день, когда прогнозный остаток опускается до точки заказа = расход за L + страховой запас. Цвет: красный — D уже наступила, жёлтый — D в ближайшие 7 дней, зелёный — иначе.
- «Уже заказано у поставщика» (количество и ожидаемая дата) — необязательное поле в карточке товара; API его не отдаёт.
- Страховой запас и вероятность дефицита — по **эмпирическому распределению ошибок** прошлых прогнозов этого товара (бэктест на его истории); при малой истории — по ошибкам категории.
- Пользователь видит: «Заказать N шт. до даты D. Риск дефицита ≈ 5%». Опционально: альтернативы («160 шт. → риск 25%, в товаре заморожено на M ₽ меньше»).
- Дополнительно показываем **оценку упущенных продаж** за прошлые дефициты (восстановленный спрос − продажи) — наглядная ценность продукта.
- Все суммы в рублях считаются **по цене продажи** (себестоимость в MVP не запрашивается).

## 6. Эксперимент (доказательство новизны)

### 6.1 Схема
- Бэктест с **разбиением по времени (rolling origin)**, несколько точек прогноза.
- Горизонты: 7, 14, 28 дней и горизонт, равный типичному сроку поставки (например, 45 дней).
- Метрики: **WAPE**, MAE, **bias** (систематическое занижение/завышение). Для решения о заказе — доля дней дефицита и средний избыточный запас в симуляции.
- Отчёт отдельно по группам: **обычные товары**, **товары с дефицитами**, **новинки**. Выигрыш ожидается в двух последних группах; на обычных товарах проигрыш/паритет допустим и честно отражается.

### 6.2 Сравниваемые методы
| Метод | Роль |
|---|---|
| Среднее по всем дням без поправок | Нижний базовый уровень |
| Среднее только по дням с наличием (формула SelSup / методика «Поставлено!») | Метод конкурентов |
| Восстановление спроса (5.1) + ETS | Вклад №1 |
| Наивный прогноз новинки (среднее за доступные дни) | Базовый уровень для новинок |
| Аналоги + смешивание (5.2) | Вклад №2 |

### 6.3 Искусственное цензурирование
Истинный спрос при реальном дефиците неизвестен, поэтому:
1. Берём участки с полной доступностью (истина известна).
2. Искусственно создаём дефицит: полное обнуление части дней и/или частичный (срез доли, имитирующий отсутствие размеров).
3. Восстанавливаем разными методами и сравниваем с истиной.
Для размеров в открытых данных распределение **смоделировано** — честно оговорить в тексте.

### 6.4 Экономический эффект
Симуляция: селлер заказывает по рекомендациям каждого метода → считаем дни дефицита, упущенную выручку, средний запас (замороженный капитал), стоимость хранения (параметр). Это аргумент практической пользы.

### 6.5 Подбор гипотез
Порог τ, параметр k, число аналогов — подбираются на валидационном периоде, проверяются на отложенном тестовом. Все решения — в DECISIONS.md.

### 7.2 Единая модель данных (все адаптеры приводят к ней)
- `products`: product_id, seller_id, category, price, attributes (JSON), launch_date, has_sizes.
- `daily_sales`: product_id, size (nullable), date, units_ordered (заказы — основной сигнал спроса), units_bought_out (выкупы, nullable). Отсутствие строки в загруженном периоде = 0 заказов.
- `daily_stock`: product_id, size (nullable), date, stock_units (nullable), in_stock (nullable). Пропущенный день — пустые значения (или отсутствие строки), **не 0**. Если известны оба поля, они должны согласовываться.

Недельные данные (VISUELLE) — отдельный режим агрегации (`frequency = "W"`, дата = понедельник недели); не смешивать молча с дневными.

### 7.3 Реальный селлер (опционально, если найдётся)
- Подключение по API-ключу «только чтение». Адаптеры WB и Ozon реализуют тот же интерфейс `DataSource`.
- **Эндпоинты, поля, лимиты — только по официальной документации** WB/Ozon для продавцов. Учитывать лимиты запросов.
- Остатки через API, вероятно, доступны только как текущий снимок → **ежедневный снимок остатков** сохраняет программа `restock-sync`, которую запускает Планировщик заданий Windows (раздел 8.3). Пропущенные дни — пропуски, а не нули. Историю до подключения дополнять выгрузками Excel из кабинета и восстановлением «поставки − продажи + возвраты».
- Критерии хорошего селлера: 30–50+ SKU, история ≥ 6 мес, 5–10 запущенных новинок, товары с размерами.
- Эксперимент на реальном селлере (если будет): в один день получить рекомендации нашего приложения и «Поставлено!» (у них есть пробный доступ), через 3–4 недели сравнить с фактом по трём группам товаров.

## 8. Продукт (MVP)

### 8.1 Сценарий пользователя
1. **Установка и первый запуск:** обычный установщик `.exe`; при первом запуске — выбрать «Демо-магазин» (данные из открытого датасета) или вставить API-ключ маркетплейса. После подключения ключа данные загружаются, и включается ежедневное обновление.
2. **Одна настройка:** срок поставки от поставщика (по умолчанию для всех товаров, можно переопределить для товара).
3. **Главный экран — одна таблица:** товар, текущий остаток, на сколько дней хватит, рекомендация «заказать N шт. до даты D», риск дефицита. Цвет строки: красный — срочно, жёлтый — скоро, зелёный — в порядке. Сортировка по срочности.
4. **Карточка товара (по клику):** график продаж и восстановленного спроса, объяснение рекомендации простым языком, упущенные продажи из-за прошлых дефицитов.
5. **Новинки:** «Похоже на эти товары: A, B, C — верно?» — подтвердить или выбрать другой аналог одним нажатием.
6. **Уведомления Windows:** «У 3 товаров запаса меньше чем на срок поставки».
7. **Выгрузка в Excel:** заказ поставщику.
8. **Свежесть данных:** в окне всегда видно «Данные от 30.10, 18:20» и кнопка «Обновить данные».

### 8.2 Требования простоты
- Не более 1 обязательной настройки. Первый полезный результат — за 2–3 минуты после первого запуска.
- Установка без ручных шагов; Python пользователю не нужен.
- Никакой статистической терминологии в интерфейсе: «риск, что товар закончится», а не «квантиль».
- Каждая цифра рекомендации объяснима одной фразой.

### 8.3 Нефункциональные требования
- **Офлайн:** интернет нужен только для загрузки данных. Без сети приложение работает на последних загруженных данных и показывает понятное сообщение.
- **Безопасность:** API-ключ хранится в Диспетчере учётных данных Windows (`keyring`), режим «только чтение»; не попадает в логи, базу и файлы настроек.
- **Ежедневный сбор данных:** `restock-sync` запускается Планировщиком заданий Windows раз в день; пропущенный запуск выполняется при следующем включении компьютера; без сети — запись в лог и завершение. Задача создаётся при подключении ключа и удаляется при удалении приложения.
- **Пересчёт рекомендаций:** после каждой загрузки данных и по кнопке.
- **Отзывчивость:** долгие операции выполняются в фоновом потоке, окно не зависает.
- **Платформа:** Windows 10/11, установщик `.exe` (PyInstaller + Inno Setup).

## 9. Архитектура

```
[DataSource]  DemoDataset | WildberriesAPI | OzonAPI   (единый интерфейс)
      ↓
[restock-sync]  консольная программа, запуск Планировщиком заданий Windows раз в день
      ↓
[SQLite]  products, daily_sales, daily_stock, settings, forecasts, recommendations
      ↓
[core]  availability → demand_recovery → forecast (ETS | analogs+blend) → order_quantity & risk → explanation
      ↓
[services]  пересчёт рекомендаций, экспорт в Excel
      ↓
[gui]  PySide6: главная таблица, карточка товара, настройки | [notify] уведомления Windows

[experiments]  backtest (rolling origin), metrics, artificial censoring, economic simulation, графики для курсовой
```
Логика `core/` не зависит от интерфейса и базы данных — работает на pandas DataFrame, одна и та же для эксперимента и для приложения. База — один файл в `%LOCALAPPDATA%\RestockPlanner\`, WAL-режим, чтобы окно приложения и `restock-sync` не конфликтовали.

## 10. Структура курсовой

1. **Анализ предметной области:** поставки на маркетплейсах, проблемы селлеров, обзор и таблица конкурентов, обзор литературы по цензурированному спросу и прогнозу новинок (15–25 источников, 5–7 ключевых), требования к системе.
2. **Проектирование:** методы 5.1–5.3 с формулами и обоснованием выбора, архитектура, схема БД, макеты интерфейса, сценарии.
3. **Реализация и оценка:** реализация, результаты бэктеста по группам, сравнение с методами конкурентов и ориентиром FreshRetailNet-50K, экономический эффект, юзабилити-тест (SUS, 5–10 селлеров, время и ошибки на задачах), CJM «было/стало».

Формулировка новизны (черновик): *«Предложен метод прогнозирования потребности в пополнении запасов для продавцов маркетплейсов, учитывающий частичное цензурирование спроса в периоды дефицита (по размерам) и отсутствие истории продаж у новых товаров, с представлением рекомендации в виде объёма заказа и вероятности дефицита».*

## 11. На диплом (вне MVP)
Распределение по складам/кластерам и дефицит по регионам; влияние малого остатка на позиции в поиске; учёт рекламы и акций; второй маркетплейс; Яндекс Маркет; глобальная модель для селлеров с большим ассортиментом; данные конкурентов (платные API аналитических сервисов); уведомления в Telegram; версия для macOS; автообновление приложения.

## 12. Риски
| Риск | Мера |
|---|---|
| Нет реального селлера | Эксперимент на открытых датасетах + искусственное цензурирование; юзабилити-тест на демо-данных |
